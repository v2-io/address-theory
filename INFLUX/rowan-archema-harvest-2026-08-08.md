## The headline: the designation + temporal machinery this corpus is theorizing has a shipped embryo, and it validates the theory in detail

Rowan's schema-evolution stack is, almost piece for piece, the Designation chapter plus the Temporal chapter already built for one narrow community (schema fields), which makes it the single best prior-art specimen the corpus has:

1. **`was:` is a stacked designator with read-time translation.** `field :full_name, :string, was: :name` = old designator stays bound through the expand-contract window; old documents are *read as* the new schema with no rewrite (keep-everything preserved — the document is never touched; the *engine* translates on read). This is O4's `|company-primary-url !{was: site}` mechanism shipped, and the SQL-lab finding F-D5 (aliases = two live binding rows; contraction = retire-with-reason) confirmed by working code.
2. **The decision log is a designation-event ledger.** Append-only, immutable, replayable (same ambiguity → same resolution in CI), with *provenance-typed sources* — `:interactive | :agent_comment (+agent_id) | :config | :cli | :auto` — and a `reason` field. This is F-D3's `designation_event` table existing in the wild, plus a refinement the lab table lacked: **the decision's source is part of the event**, giving trust-tiering and audit for free. O10's constraints-carry-removal-reasons appears here too (`reason:` on every resolution).
3. **Rename-ambiguity is expected-cardinality machinery.** The differ's heuristic — 1-removed + 1-added + same-type → `:possible_rename` conflict, *ask don't guess* — is "never a silent best-guess" (engine obligation 3) implemented: ambiguous narrowing degrades to choices (`[:rename, :separate]`), resolutions are recorded, recorded resolutions replay. The theory's obligations read like a spec this code was built to.
4. **Branch safety is a NEW designation case the chapter didn't have: collision-by-merge.** Two branches rename `name` differently (`full_name` vs `display_name`); each is internally consistent; the *merge* of two naming communities creates the collision, detected because both histories are event logs that can be compared. Neither dangle nor second-mint — a third collision mode, arising only because communities fork and rejoin. Feeds `disc-designation-cases`.
5. **The upcast path is a live compositional-sequence specimen.** `upcast_path(from_version)` collects per-version transform blocks and folds them in order — exactly [[claim-sequence-causes]] cause 3: composition, foldable because the consumer wants only the endpoint and application is associative-in-sequence. Version chains are addresses through time whose segments are transforms. Feeds the Temporal chapter and the sequence-causes exhaustiveness probe (a supporting instance, not a fourth cause).
6. **`_schema: type/version` is self-description as a carried designator** — the document names its own schema community + version (O13's "aspirational schema" rung, shipped as a field), and `since:`/`deprecated:`/`removed:` per-attribute = designator lifecycle down at the field grain, enabling "what did User look like at v1.5?" — an as-of query over schema history. Straight into Temporal & Version Dynamics.

## Second theme: SQL is a projection target, never the semantics (ADR-003)

Rowan's founding schema ADR inverts the RDBMS-first tradition: constraint vocabulary comes from the *richer* document side (JSON Schema's oneOf/anyOf/if-then/dependentRequired, in `constraints.rb`); schema-layer validation is canonical; RDBMS constraints are **best-effort projections, defense-in-depth only**. Two consequences for this corpus:

- Direct support for our SQL-stage framing (the lab teaches; it doesn't bound). The warning it adds: never let what SQL can express trim the RA — rowan hit exactly that with polymorphic FKs and solved it by making SQL the lossy projection.
- The "three-worlds unification" (RDBMS relationships/ACID + document expressiveness/readability + event-sourcing temporality/audit) **is LUSS's ambition statement**, made by a shipped system — and rowan's multi-store composition (`store :primary, :sequel` + `store :audit, :jsonl, immutable: true`; cross-store relationships; cross-adapter evolution consistency tests) is prior art for LUSS fluxes. Feeds `form-luss` beside the NORMS-reduces hypothesis.

## Third theme: empirical grounding for Part III cases (the 1,950-migration survey)

Six evolution ladders with forward/backward asymmetry, from real migrations across 15 repos (dataset flagged unverified upstream — treat frequencies as indicative): normalization (blob→columns→table), cardinality (1→N→M:N→rich-join), type-refinement, **identity** (autoincrement→UUID→natural-key→composite — seeds designation cases with observed frequency: 1.6%, asymmetric), **temporal** (current-state→soft-delete→versioned→event-sourced — the Temporal chapter's case ladder, 4.0%, asymmetric), constraint (14.1%, symmetric). Only **8.5% of migrations are asymmetric** — most schema change is reversible, and the asymmetric minority is concentrated exactly in identity + temporal, i.e. in this corpus's territory. The steward's event-sourcing instinct gets a frequency argument: the ladders' one-way direction all point *toward* event-sourcing, never back.
