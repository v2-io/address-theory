## The intuitions, as I now hold them

1. **"All stores are compositions, even single-entry ones."** There is no simple/complex bifurcation anywhere in the model — a lone adapter is the degenerate composition, and the store-api-clarification exists precisely to kill the one place a bifurcation had crept in (`Resource.adapter` returning adapter-or-MultiStore). The airtight-abstraction move is: *don't special-case simplicity; make simplicity the unit case of the general shape.* LUSS translation: a single `.udon` file is already a store — a one-entry composition — not a pre-store stage on a ladder. The layout ladder should be compositions all the way down, not a sequence of increasingly special kinds.

2. **The composition IS the orchestrator.** Configuration and runtime router are one object; there is no third thing that "interprets" config. Even a single-entry composition routes (it just routes everything one place). This lands directly on [[def-cardinality-and-resolution]]'s engine-and-perspective split: rowan's answer to "resolution engine relative to a perspective" is that *the composed perspective is the engine* — composing the declaration produces the executing thing, not input for one.

3. **Semantics live entirely in the composition layer; mechanism is quarantined below the adapter contract.** The entry tuple `(role, mode, adapter, params, resolver)` puts *purpose* (role — arbitrary symbols, behavior inferred from prefix, overridable), *direction* (mode), and *mechanism* (adapter) in separate seats, and all routing semantics (`:write_primary`, `:append_events`, `:write_fanout`, `:read_cache`) attach to roles, never to adapters. This is WHY unimplemented adapters don't matter: any adapter satisfying the small CRUD contract slots into every composition ever written. The LUSS deliverable, by direct analogy: the composition algebra + role/behavior semantics + the entry anatomy — with directory shapes, file granularity, and every physical concern below a contract line where they can vary freely.

4. **The merge algebra is precise, and it reconciles with udon's no-last-wins in an instructive way.** Ordered merge, override by `(role, mode)` key; `:readwrite` is one coherent entry (NOT sugar for two — a Memory adapter split in two would need synchronization with itself); partial override *demotes* rather than clobbers (add `:read` over `:readwrite` → incumbent demotes to `:write`; a subsequent explicit `:write` errors); duplicate registration of a name raises. And every merge operation is recorded — `CompositionHistoryEntry(action, key, entry, previous_entry, source)` — so a resolved composition can report its own derivation with attribution. So the overrides are not silent last-wins: they are **typed rebinding events with recorded provenance**. In this corpus's vocabulary: composition entries are designators in a `(role, mode)` naming community, rebinding is evented, and the ledger travels with the resolved thing.

5. **Dynamism is fenced, menu-vs-knob shaped.** Three levels were identified: (1) per-entry param computation, (2) per-entry adapter selection, (3) runtime composition mutation. Levels 1–2 supported; **Level 3 explicitly rejected** ("speculative complexity with no concrete use case" — grounded in simulation + autopax production usage). Compositions are predefined, immutable, frozen; dynamism selects *between* predefined compositions; resolvers return a Symbol or a params-Hash, never a new composition. LUSS translation: perspectives/stores are declared artifacts; acts may select among declared perspectives (that's the resolver seat), but nothing mutates a perspective mid-resolution. Same fence shape as the theory's menu-vs-knob.

6. **Names before instances, with mint-time policing.** Resources reference stores by registered name only (inline adapter construction at resource level is the deprecated pattern); instances live in the registry, shared; `def_store :primary` twice raises. The registry is a naming community with collision policing at mint — D8's discipline, applied to stores themselves. The adapter-config vs operation-params split (registration-time shared identity vs per-entry use) is the same cut as community-owned binding vs act-carried parameters.

7. **The honest opens are paths-theory questions wearing store clothes** (open-questions 14–16, 21): cross-store filter mapping = capability negotiation among perspective members (an act using an operator one member can't evaluate); projection staleness/freshness = found-but-stale + read-your-writes, unhandled; failure recovery = event-as-truth + idempotent rebuild, unimplemented. When the LUSS row drafts, these are the questions it inherits — rowan priced them and left them open on purpose.

## From the tests (second first-hand pass, steward-prompted: `multi_store_test.rb` whole, `heterogeneous_multistore_spec_test.rb` §1–4, `cross_adapter_property_test.rb` whole)

8. **Entry ≠ instance — and this dissolves the docs' `:readwrite` contradiction.** Shipped semantics (multi_store_test): `store :primary, :readwrite, :memory` produces **two entries** — `get_entry(:primary, :read)` and `(:primary, :write)` both exist — over one shared adapter instance. ADR-001 ("one entry, or two Memory instances would need synchronization") and the clarification ("always two entries") were arguing about *different objects*: the entry is a **seat/claim** in the routing algebra; the instance is the mechanism. Two seats, one mechanism — both docs were right about their own object. Theory payoff: seat-identity and mechanism-identity are separate axes, and a contradiction that survives in prose can be an object-conflation the executable semantics has already resolved.

9. **Build-free, bind-checked — recognition-total/judgment-layered at the store layer.** Compositions construct without validation (any roles, any adapters); obligations fire at `composition.bind(resource)` — and the checked obligation is **behavioral, not nominal**: the error is "must have write_primary *behavior*", satisfied by `:primary_backup` or any role carrying the behavior, never by a name check. Constructing a perspective never fails; *binding it to a consumer* is the validation moment. (Also: role names are an open set; behaviors are a closed validated set — `behavior: :invalid` raises at entry construction. The open/closed line runs between naming and semantics: name anything, but semantics come from a fixed menu.)

10. **Role behaviors are per-role dispositions of one act.** A single `create` fans out as *different shapes per role*: the primary gets the record; the event store gets a semantic event (`{event_type: "created", aggregate_id, data, metadata: {timestamp, schema_version}}`) — not a row copy; the projection gets the record; the cache gets invalidated. The fan-out is not replication — it is one act projected into each role's idiom by its behavior. This is the Outcomes chapter's `disp:` vocabulary, shipped and tested.

11. **Events carry their own schema version; replay composes two folds.** `test_rebuild_projection_upcasts_old_events`: a v1.0.0 event (old field name) written directly to the file is upcast during `rebuild_projection!` via the resource's `upcast from:` block, keyed off the event's *own* `metadata.schema_version`. Re-materialization = the event fold composed with the per-event version-upcast fold — each event self-declares its dialect, translated at replay. Straight into the Temporal chapter beside upcast-on-read.

12. **The property tests are an executable decisions ledger.** Every property in `cross_adapter_property_test.rb` opens with a `Deciding:` annotation naming the semantic ruling it enforces — string/symbol key equivalence ("inconsistent handling leads to silent data loss"), nil round-trips as nil, **empty string distinguishable from nil**, and matcher *partition laws* (`eq + neq = all records, no overlap`; `gt + lte partitions`; `gte = gt + pivot`). Two transfers: (a) this is how "serialization symmetric" (the matrix-collapse proposition) is actually being earned — law by law, as adversarial properties, not asserted; (b) for the RA design: state the matcher algebra as partition/complementarity laws and engine conformance becomes *passing the law set* — the store-conformance shape from §8 of the pipeline note, now seen working. And the annotations themselves are a verisectorium-shaped specimen: decisions recorded where they execute, replayable by construction.

*(Third pass, steward-directed: `multistore_spec_test.rb` + `multistore_migration_spec_test.rb`, both whole.)*

13. **Mint-once, fan-out-many — co-reference across stores holds by construction.** The behavioral contract states it as SPECIFICATION: projections MUST receive **the same generated values** as the primary (same UUID, same timestamps) — "prevents ID/timestamp divergence between stores." So generation (identity minting, timestamping) happens *once, in the act, upstream of the role fan-out*; every store receives the same resolved record, never re-derives its own. Theory payoff: this is the precondition for over-determination verification (D6, resolve-by-one-verify-by-another) working across stores at all — co-reference between a primary row, a projection file, and an event's `aggregate_id` is checkable only because identity assignment was a single upstream event. Minting is an act-level operation; stores are only ever *told*.

14. **One schema evolution, per-member application moments — form-resolve-moments shipped for schema.** The migration spec's header table is the finding: the *same* declared change (`was:`, `upcast from:` — declared once, on the Resource) applies as **SQL DDL at deploy-time, before reads** for Sequel members; as **read-time upcasting, during each read** for YAML/JSONL members; as nothing for Memory (ephemeral). "File-based stores don't need DDL — their evolution is transparent and non-destructive (old data stays as-is on disk)." The store kind is the *decider of the resolution moment* of the schema change — exactly the role [[form-luss]] assigns LUSS — and the generator fires only where materialization is the mechanism (ISSUE-049: memory-only/yaml-only/jsonl-only compositions generate no migration; a change is "found" only for SQL members). Meanwhile schema *truth* is store-invariant: snapshots of identical attribute sets over memory vs yaml are equal modulo table name. One logical change, one truth, N moments — live/once/materialized as a per-member property, not a global election.

15. **Constraints degrade per-member without changing meaning — ADR-003 executed.** A cross-store `belongs_to` (parent in memory, child in YAML) generates no FK constraint — it *can't* — and the relationship still works, because canonical validation lives at the schema layer and the SQL FK was only ever defense-in-depth projection. Also on record: non-primary Sequel projections are deliberately **not** auto-migrated ("derived views, potentially managed separately") — a derived perspective's materialization schedule is its own concern, not the primary's. And the rename pair (ambiguous change → conflict requiring resolution; `was:` → clean `rename_column`, no conflict) shows the decision-carrying declaration *removing* an expected-cardinality ambiguity at diff time — the recorded intent is what converts found-many-interpretations into found-one.

## What this corrects in my own prior notes

The store-concepts harvest's frame (implemented-vs-conceptualized adapters; "layout ladder extends rather than ports") asked the wrong question. The adapter census is nearly irrelevant: the intuition Joseph pointed at is that **an airtight composition algebra makes the store inventory an open set by construction** — the direct sibling of udon's own dialect move (frozen bare set + envelopes = additive typing; small adapter contract + composition algebra = additive storage). That parallel — *the same additivity defense at the storage layer that CORE built at the type layer* — is, I think, the single most load-bearing thing rowan contributes to LUSS, and none of the secondhand passes surfaced it.
